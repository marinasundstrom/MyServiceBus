# Declare consumers with methods or consumer types.

<p className="docs-summary">Attributed methods are an alternative declaration style for the same consumer pipeline. Their signatures bind messages and dependencies without requiring one interface implementation or class per message.</p>

## The corresponding Java declaration

Java uses <code>@MessageConsumer</code> because <code>Consumer&lt;T&gt;</code> already names its interface-consumer contract. Its binding and endpoint semantics match the C# declaration without requiring a shared attribute or interface.

## The Kotlin function projection

Kotlin declares the same idea as a top-level suspending function. Its message is bound directly, other parameters come from the delivery scope, and the returned value becomes the response.

<CodeViewer code={kotlinFunctionExample} label="Kotlin consumer function" language="kotlin" />

## Return a response

A request handler can return its response contract directly. MyServiceBus awaits the operation and sends the value through the active consume context, preserving the normal request correlation metadata. C# supports <code>Task&lt;T&gt;</code> and <code>ValueTask&lt;T&gt;</code>; Java supports <code>CompletableFuture&lt;T&gt;</code> and <code>CompletionStage&lt;T&gt;</code>.

<CodeViewer code={responseMethodExample} label="C# request-response consumer method" language="csharp" />

<CodeViewer code={javaResponseMethodExample} label="Java request-response consumer method" language="java" />

Returning a response does not make the context parameter mandatory. Add <code> ConsumeContext&lt;TMessage&gt;</code> when the method needs headers, correlation identifiers, addresses, or other receive metadata; otherwise the message and application services are enough.

A response-bearing method requires an incoming request with a response address. If the method fails—or no response address is present—consumption fails through the normal retry and fault pipeline. Synchronous response values are not supported.

## Choose by size and grouping

Use an <code>IConsumer&lt;T&gt;</code> class when a consumer is substantial enough to deserve its own type. Use consumer methods when the containing class mainly groups related handlers and acts as their de-facto namespace. Neither declaration style changes the message contract or wire behavior.

C# currently requires methods to be contained by a type. That containing type is organizational and is not itself the consumer. Static methods do not cause the container to be instantiated or registered as a service.

## Parameter binding

The method name does not determine eligibility or the message contract. <code>Consume</code>, <code>ReceiveOrder</code>, <code>Handle</code>, and other function names are all valid; the signature determines the binding.

## Group methods by endpoint

A class-level <code>[Consumer(&quot;orders&quot;)]</code> discovers all eligible methods on the class and maps them to one endpoint. Grouping is an optional organizational benefit: related handlers can stay together instead of being spread across separate consumer classes. The endpoint binds every declared message type; if two methods on that endpoint consume the same message type, both methods run.

## Override or configure the mapping

The attribute string is the receive endpoint name. A method-level attribute can override the class mapping for an individual method, and an explicit fluent value overrides both. Explicit names are never replaced by an endpoint-name formatter.

<CodeViewer code={overrideExample} label="C# consumer method endpoint override" language="csharp" />

<CodeViewer code={fluentExample} label="C# fluent consumer method mapping" language="csharp" />

A bare method-level <code>[Consumer]</code> still declares a consumer. Its endpoint name comes from the method name, so the example below maps to <code>OrderSubmittedConsumer</code>.

<CodeViewer code={conventionExample} label="C# method-name endpoint convention" language="csharp" />

Endpoint precedence is: explicit fluent mapping, method attribute, class attribute, then convention.

Method containers do not implement an <code>IConsumer</code> marker or share a consumer interface with another framework.

## Mark only the method

The containing class does not need an attribute. A method-level attribute is a complete declaration in both reflection and generated discovery, which also keeps the model suitable for external integrations that cannot annotate a container.

## Override an interface consumer endpoint

The attribute is also an alternative to fluent endpoint mapping for a normal <code>IConsumer&lt;T&gt;</code> class. In that case it overrides the consumer&apos;s endpoint name; it does not turn <code>Consume</code> into a separately discovered method consumer.

## Reflection or generated dispatch

Registration is an application choice. Explicit registration names a consumer implementation or supplies a typed method/function invoker without discovery. Reflection inspects explicitly selected declarations at startup. The C# generator, Java JSR 269 processor, and Kotlin KSP processor scan their compilations and emit the explicit typed registrations for the application. Every path enters the same runtime pipeline.

<div className="docs-feature-grid">
  <div><span>01</span><h3>Explicit</h3><p>Register consumer implementations or typed invokers directly for maximum control and no discovery.</p></div>
  <div><span>02</span><h3>Reflection</h3><p>Discover bounded assemblies, classes, or function references with a startup and AOT tradeoff.</p></div>
  <div><span>03</span><h3>Generated</h3><p>Let build-time tooling emit direct registrations for predictable startup and closed-world deployment.</p></div>
</div>

<ul className="check-list">
  <li>Assembly discovery builds method descriptors and invokes methods through reflection.</li>
  <li>The C#, Java, and Kotlin generators bind parameters and call methods or functions directly.</li>
  <li>Both modes use the same receive, retry, fault, telemetry, and dependency scopes.</li>
  <li>Java reflection inspects only explicitly registered classes; it does not scan the classpath.</li>
  <li>Applications may mix styles when different components need different tradeoffs.</li>
</ul>
