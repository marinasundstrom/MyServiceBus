# Commit application state and messaging intent together.

<p className="docs-summary">The MyServiceBus PostgreSQL outbox gives C# and Java services one durable transaction for a database change and its outgoing message. The matching inbox protects consumer-side effects when brokers redeliver.</p>

<div className="callout callout-accent">
  <strong>Why this belongs in the framework</strong>
  <p>An application should not have to rebuild durable envelope storage, multi-replica leasing, stable message identity, retry state, and duplicate detection for every service. These are shared messaging guarantees, so MyServiceBus is making them a primary production capability.</p>
</div>

## A familiar MassTransit model

MyServiceBus follows MassTransit's useful distinction between a **Bus Outbox** for messages produced in an application scope and a **Consumer Outbox** that combines inbox deduplication with outgoing capture around a consumer. Teams can use [MassTransit's outbox documentation](https://masstransit.massient.com/concepts/outbox) as conceptual background instead of learning new terminology for the same architectural boundary.

MyServiceBus documentation remains authoritative for setup, supported behavior, and release status. MassTransit configuration snippets are not source-compatible MyServiceBus examples, and behavior that MyServiceBus has not verified is not implied by conceptual compatibility.

## Replace two unrelated commits with one durable hand-off

Publishing to a broker after updating a database creates a failure gap: the database can commit while publication fails, or publication can succeed while the database rolls back. A distributed transaction is rarely available across both resources.

The outbox records the final serialized envelope in the same PostgreSQL transaction as the application change. A separate dispatcher leases only committed records and delivers them later.

<div className="flow-line" aria-label="Transactional outbox flow">
  <span>Update application state</span><b>+</b><span>Store outgoing intent</span><b>→ commit →</b><span>Lease and dispatch</span><b>→</b><span>Broker</span>
</div>

If the dispatcher exits after the broker accepts a message but before PostgreSQL records completion, the record becomes eligible again. MyServiceBus reuses its original message identity, allowing an inbox-protected consumer to recognize the duplicate.

## What works today

The C# package `Sundstrom.MyServiceBus.PostgreSql` and Java module `io.github.marinasundstrom.myservicebus:myservicebus-postgresql` provide equivalent behavior:

- an idempotent, versioned PostgreSQL schema;
- a writer that requires the application's active transaction;
- opt-in Bus Outbox capture through ordinary scoped publish and send endpoints;
- a factory that captures the final serialized send context and its envelope metadata;
- atomic leasing with `FOR UPDATE SKIP LOCKED` for competing replicas;
- persisted attempts, retry time, lease ownership, and dispatch state;
- complete envelope storage with stable message and correlation identities; and
- inbox acquisition and completion keyed by consumer scope and message identity.

Both implementations are tested against PostgreSQL 17.6 with Testcontainers. The suites cover rollback and commit behavior, scoped publish/send capture, envelope rehydration, concurrent disjoint leases, and atomic inbox completion with an outgoing outbox record.

## Write with the application transaction

The caller owns commit and rollback. MyServiceBus refuses to write without an active caller-owned transaction, preventing the outbox record from silently committing separately from application state.

Enable Bus Outbox during registration. In an application service scope, attach the scoped session to the active PostgreSQL transaction. Calls through the scoped publish and send contracts then store the final envelope rather than contacting the broker.

### C#

```csharp
services.AddServiceBus(configurator =>
{
    configurator.UseBusOutbox();
    configurator.UsingRabbitMq((_, rabbit) => rabbit.Host("localhost"));
});

await PostgreSqlSchema.EnsureCreatedAsync(dataSource);
await using var scope = serviceProvider.CreateAsyncScope();
await using var connection = await dataSource.OpenConnectionAsync();
await using var transaction = await connection.BeginTransactionAsync();

// Execute the application UPDATE/INSERT using this transaction.

using (scope.ServiceProvider.GetRequiredService<OutboxSession>()
    .UsePostgreSql(connection, transaction))
{
    var publish = scope.ServiceProvider.GetRequiredService<IPublishEndpoint>();
    await publish.Publish(new OrderSubmitted(orderId), context =>
        context.CorrelationId = orderId.ToString());
}

await transaction.CommitAsync();
```

### Java

```java
services.from(MessageBusServices.class).addServiceBus(configurator -> {
    configurator.useBusOutbox();
    configurator.using(RabbitMqFactoryConfigurator.class,
            (context, rabbit) -> rabbit.host("localhost"));
});

PostgreSqlSchema.ensureCreated(dataSource);
try (ServiceScope scope = serviceProvider.createScope();
     Connection connection = dataSource.getConnection()) {
    connection.setAutoCommit(false);

    // Execute the application UPDATE/INSERT using this connection.

    ServiceProvider scoped = scope.getServiceProvider();
    try (OutboxSession.Registration ignored =
            PostgreSqlOutboxSession.useTransaction(
                    scoped.getRequiredService(OutboxSession.class), connection)) {
        PublishEndpoint publish = scoped.getRequiredService(PublishEndpoint.class);
        publish.publish(new OrderSubmitted(orderId), context ->
                context.setCorrelationId(orderId)).join();
    }

    connection.commit();
}
```

Resolve endpoint contracts from the same scope as the session. Calling `IMessageBus` / `MessageBus` directly intentionally bypasses capture. Nested registrations are rejected. Scheduled messages inside an active outbox session currently fail clearly; durable scheduling will be handled in a separate slice.

## Protect consumer effects with the inbox

Acquire the inbox identity in the transaction that owns the protected application change. `Acquired` may execute the effect. `Completed` is a safe duplicate and skips it. `InProgress` must remain eligible for retry.

For an acquired delivery, write responses and new messages through the acquisition's outbox, mark the inbox record complete, commit PostgreSQL, and only then settle the broker delivery. A crash between the database commit and broker settlement produces a safe redelivery rather than a repeated database effect.

## Understand the guarantee

This design provides effectively-once protected PostgreSQL effects when the application uses the transaction boundary correctly. It does not promise globally exactly-once delivery, cross-database atomicity, or automatic idempotency for external API calls.

The next implementation step is framework-owned hosted dispatch and broker adapters, followed by Consumer Outbox middleware for responses, publications, and faults produced while consuming a message.
