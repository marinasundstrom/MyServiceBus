# Keep mediator intent while replacing handlers in controlled slices.

<p className="docs-summary">MyServiceBus provides MediatR-familiar Send and Publish semantics, inferred query responses, dedicated handler interfaces, and generated registration. It is a semantic migration path—not a binary-compatible replacement package.</p>

## 1. Preserve the contract intent

Commands and queries use exactly-one-handler <code>Send</code>. Notifications use fan-out <code>Publish</code>. Implementing MyServiceBus <code>IRequest&lt;TResponse&gt;</code> keeps the familiar inferred result call, so a query remains{' '} <code>OrderView order = await mediator.Send(new GetOrder(orderId));</code>.

## 2. Port one vertical slice

<ul className="check-list">
  <li>Change the request and notification marker namespaces deliberately; the familiar names can otherwise hide an accidental mixed dependency.</li>
  <li>Port the corresponding request handler, notification handlers, validation, and tests together.</li>
  <li>Register the new handlers with <code>AddHandler</code> and resolve the MyServiceBus <code>IMediator</code>.</li>
  <li>Keep the old MediatR registration for untouched slices until their callers have moved.</li>
  <li>Avoid registering the same command in both mediators behind one ambiguous application abstraction.</li>
</ul>

## 3. Rebuild pipeline behavior intentionally

MediatR pipeline behaviors are not copied automatically. Map validation, logging, authorization, transactions, and exception policy to MyServiceBus consume pipeline filters or application decorators, then assert ordering, scope, cancellation, and exception behavior. The <Link href="/docs/filters">filters and middleware guide</Link> shows the equivalent C# and Java mediator registration. A handler test passing does not prove the surrounding pipeline has equivalent semantics.

## 4. Choose generated or explicit registration

Explicit <code>AddHandler</code> registration is a clear migration baseline. Add the C# source-generator package and <code>AddGeneratedConsumers()</code> when compile-time registration and direct generated dispatch are useful. This removes reflection from handler discovery and invocation; it does not imply that every dependency or serializer in the application is reflection-free.

## 5. Verify the semantic differences

<ul className="check-list">
  <li><code>Send</code> fails when zero or multiple compatible handlers are registered.</li>
  <li><code>Publish</code> invokes every compatible local handler and waits for their pipelines.</li>
  <li>Cancellation and terminal exceptions reach the caller.</li>
  <li>Handler and dependency scopes match the application&apos;s expectations.</li>
  <li>Any notification concurrency or ordering assumption is tested rather than inferred from familiarity.</li>
</ul>

<div className="callout">
  <strong>A later distributed boundary is optional</strong>
  <p>Handler and consumer shapes share the same runtime, so a contract can later move behind RabbitMQ or Azure Service Bus. That is an architectural change with delivery, serialization, idempotency, and failure implications—not an automatic mediator toggle.</p>
</div>

Java has the equivalent <code>Mediator.send</code>/<code>publish</code>, typed request, and handler experience. The JVM requires <code>responseType()</code> on a typed request because generic response information is erased at runtime.
