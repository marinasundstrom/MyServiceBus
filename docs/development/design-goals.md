# MyServiceBus Design Goals

- **Enterprise Production Confidence**: Design for enterprises running business-critical messaging. Every production-ready claim must be scoped to named capabilities and backed by explicit delivery guarantees, failure tests, secure deployment guidance, operational telemetry, reproducible resilience evidence, and a predictable support lifecycle. Production confidence takes priority over expanding the feature catalog.
- **Permissive Open-Source Core**: Keep the core C# and Java runtimes available under a permissive open-source license. Sustainable support or hosted offerings may be developed around the project, but adopting the core runtime must not require a commercial runtime license.
- **Focused Improvement on MassTransit**: Build on MassTransit's proven messaging model while improving the boundaries MyServiceBus deliberately owns: cross-language parity, generated dispatch, explicit compatibility and delivery evidence, and a smaller portable core. Do not turn that motivation into an unscoped claim of universal superiority.
- **Explicit MassTransit Compatibility**: Preserve wire compatibility and the portable messaging semantics needed for interoperability. Claim transport-profile compatibility only where addressing, topology, and settlement behavior are covered by conformance tests; source compatibility and complete MassTransit feature parity are not goals.
- **Broker-Backed Product Scope**: Optimize the stable runtime and topology model for basic broker-backed service-bus scenarios that can replace MassTransit. HTTP callbacks, webhooks, realtime sessions, and other non-broker technologies may reuse lower-level components, but they do not shape the bus abstraction without demonstrated need.
- **Deliberate Modernization**: Retain MassTransit behavior when it supports protocol interoperability, migration, or a useful shared concept. Legacy edges may be replaced or omitted when they no longer serve those goals, provided the divergence and migration impact are explicit and versioned where necessary.
- **MassTransit Structural Familiarity**: Use MassTransit's structural vocabulary, behavioral model, and common configuration path across the portable clients so developers can start with little conceptual translation. Preserve wire behavior where interoperability requires it and keep interfaces recognizably MassTransit-like, while allowing preview APIs and obsolete historical edges to evolve when that improves MyServiceBus.
- **Compatibility Before Idiom**: Evaluate a feature in the order `concept compatibility → behavior compatibility → API compatibility (contracts + behavior) → idiomatic design`. Preserve MassTransit's concept first, then its observable runtime semantics. Adopt its interface when both the contract and behavior remain a sound fit. Where platform capabilities or conventions differ, expose an idiomatic C# or Java shape that still maps unambiguously to the shared concept and verified outcomes.
- **Cross-Language Conceptual and Structural Parity**: Moving between clients should require minimal adjustment. C# and Java should use closely corresponding APIs and implementation stages wherever their similar language models allow it. Future platforms should preserve recognizable factories, configuration, topology, mapping, settlement, and test concepts through the closest native approximations, even when their surface idioms cannot match as closely.
- **Aligned Implementations**: The C# and Java codebases, including their test harnesses, should evolve together so that features and behavior stay in sync.
- **Owned Abstractions**: Present a MassTransit-like surface through a single `IMessageBus` and self-contained envelope, fault, and pipeline contracts so the bus can evolve independently of MassTransit.
- **Isolated Transports and Runtime Dependencies**: Keep brokers and runtime infrastructure behind pluggable adapters and rely on lightweight DI and logging abstractions so implementations can change without rippling through application code.
- **First-Class Extensibility**: Expose filter and pipeline registration, retry policies, and request client factories within MyServiceBus APIs rather than MassTransit extensions to allow future divergence in pipeline strategy.
- **Definitions Before Topology**: Route consumer-specific endpoint and execution policy through a definition layer before materializing topology. Keep definition semantics aligned across .NET and the JVM while allowing C#, Java, and Kotlin to project native configuration APIs.
- **Capability-Aware Transports**: Model transport features as native, emulated, or unsupported so additional brokers and event streams retain their real delivery, ordering, settlement, and replay semantics.
- **Optional Operations Plane**: Keep inspection, monitoring, and dashboards outside the delivery-critical core and expose them through stable programmatic APIs.
- **Application-Oriented Operations Experience**: Organize the supplied dashboard around one distributed application and its participating services or sub-applications before progressively revealing buses, endpoints, topology, transports, and broker infrastructure. Keep the underlying monitoring contracts technically precise so alternative engineering-focused dashboards and tools can consume the same data.
- **Concept-and-Behavior Specification**: Define MyServiceBus first through language-neutral concepts, relationships, operations, and observable outcomes. Interfaces and native types belong to implementations and should not become portable requirements merely because C# and Java expose similar shapes.
- **Executable Specification**: Treat normative behavior together with shared fixtures, cross-language scenarios, and transport-profile interoperability tests as the source of truth for every client and adapter. Use the reference implementations to evolve and validate that model, resolving conflicts explicitly while the specification matures.
- **Alignment Before Stability**: While the protocol is still being aligned, MassTransit-compatible wire behavior takes precedence over preserving earlier incompatible MyServiceBus behavior. Stabilization and backward-compatibility commitments must be explicit future decisions.
- **Fundamentals Before Advanced Patterns**: Establish MassTransit-familiar registration, topology, delivery, request, fault, retry, and settlement behavior before adding sagas, state machines, or outbox features. If those advanced patterns are added, preserve their fundamental behavioral model and recognizable surface concepts in C# and Java without requiring MassTransit's implementation or foreclosing a MyServiceBus-native state-machine design.
- **Idiomatic and Approachable Clients**: Each client should feel native to its platform and expose a clear default path. Shared internal abstractions must not make ordinary users adopt a framework or understand infrastructure they do not need to customize.
- **Modern APIs Within Explicit Baselines**: Use current C#/.NET and Java idioms available within each published runtime baseline. Align contracts and behavior without reducing either client to the other platform's syntax or to the lowest shared language feature. Treat Java bytecode/API compatibility and JDK build/runtime selection as separate decisions; treat the .NET target framework and experimental future targets as explicit release boundaries.
- **No Mechanical Translation**: C# namespaces, project boundaries, inheritance models, overloads, and language features do not prescribe Java packages or class structure, and Java conventions do not prescribe C#. Alignment is required at the conceptual and behavioral boundaries, not through one-to-one source translation.
- **Queryable Topology as a Foundation**: Model messages, endpoints, consumers, and bindings with corresponding, idiomatic C# and Java APIs. Runtime provisioning, inspection, and future dashboards must project from this model instead of independently inferring topology.
- **Mediator as Local Execution**: Reuse consumers and pipelines in process for tests and deliberately local interactions, while directing externally observable events through the broker-backed bus instead of maintaining parallel mediator and bus paths by default.
- **Mediator as a Primary Product Path**: Make MyServiceBus a credible MediatR replacement for commands, queries, notifications, and response handlers, with dedicated C# and Java handler APIs, generated dispatch, permissive licensing, and no requirement to adopt a broker. Preserve a coherent migration path when a local boundary later becomes distributed.
- **One Supported Bus per Application**: Keep hosting, dependency injection, lifecycle, topology, and telemetry centered on one logical bus. Multiple hosted bus instances are out of scope unless a concrete cross-platform use case later justifies an idiomatic C# and Java design.
